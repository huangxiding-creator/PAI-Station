# FDE企业AI交付项目，究竟该如何报价？

原创 FDE中国 2026-09-06 20:15 浙江

一套能力分层、复杂度判断和组合报价方法，让价格真正对应交付责任与业务价值。

同样是做一个客服 Agent，有人报 10 万元，有人报 50 万元，还有人报到 100 万元以上。

差别真的只是团队名气、模型成本和人天单价吗？

很多时候，三家公司嘴上说的是同一个项目，实际承诺的却是三种完全不同的交付能力：第一家做一条能演示的工作流，第二家让 Agent 接入真实系统并完成任务，第三家还要处理权限、异常、监控、审计和持续运营，让它成为企业生产系统的一部分。

界面可能都只是一个聊天框，水面下的系统复杂度和责任边界却可能相差十倍。

因此，FDE 项目报价不应该先问“一名工程师一天多少钱”，也不应该先选固定价、订阅或效果分成。第一步是给交付能力分层：这次到底要交付一条 Workflow、一个 Agent、一套生产级流程系统，还是一套复杂企业 AI 系统？

层级确定之后，范围、团队、验收、风险和收费方式才有讨论基础。

报价的起点不是人天，而是交付能力与责任边界。

最基础的 FDE 交付，是把一个重复任务变成可运行的工作流。

例如合同信息提取、商品文案生成、官网线索初筛、客服知识检索或会议纪要入库。它通常有明确输入和输出，连接一到两个数据源，主要动作可逆，高风险结果仍由人工确认。

这一层的难点不是“调用一次大模型”，而是把任务拆清楚：什么时候触发，读取哪些数据，执行哪些步骤，输出到哪里，什么情况视为失败，谁负责人工接管。

合理交付物应包括流程定义、提示与规则、必要的 Connector、测试样本、失败边界、运行文档和有限试点。验收更适合看字段完整率、关键错误率、处理时间、人工修改率和任务完成率，而不是只看 Demo 是否流畅。

因为范围相对稳定，这一层通常适合固定项目价；若 Workflow 可以跨客户复用，还可以拆出 Skill 或 Workflow 资产费。

第二层：Agent，交付能够判断并调用工具的任务执行者

Agent 比 Workflow 多了一层动态决策。它要理解任务状态、选择工具、组合步骤，并根据中间结果调整下一步。

例如销售 Agent 需要读取 CRM、查询产品与价格、判断线索等级、生成跟进建议并写回商机；客服 Agent 可能要识别意图、检索知识、查询订单、执行售后流程，再决定回答、转交还是要求人工审批。

一旦 Agent 能调用真实工具，交付责任会明显扩大。工具选错、参数写错、循环调用、上下文膨胀、越权访问和异常重试，都会从“回答不好”升级成真实业务风险。

这一层除了任务效果，还要验收工具选择正确率、参数正确率、执行成功率、权限边界、人工接管率、单任务成本和完整追踪。价格也不再只对应开发功能，而要覆盖 Agent 编排、工具接入、Eval、护栏和受控上线。

因此，Agent 项目更适合“实施费 + Agent/Skill 资产费”；进入稳定生产后，再加入按 Task、Conversation 或调用量计费。

第三层：生产级流程系统，交付一条可持续运行的业务能力

当 AI 进入客服、销售、供应链、法务或财务核心流程，项目就不再只是一个 Agent。

它通常要跨 CRM、ERP、工单、身份、审批和数据平台，处理正常路径与大量例外；同时具备细粒度权限、日志审计、灰度发布、监控告警、回滚、人工接管、成本预算和版本管理。

这一层最容易出现“PoC 看起来成功，生产却跑不起来”。原因往往不在模型，而在脏数据、遗留接口、权限审批、并发、采用方式和异常责任没有被设计。

NIST AI RMF[1]要求 AI 系统在接近真实部署的条件下接受评估，并在生产环境持续监控功能与行为。换成合同语言，就是上线不是终点：试点期、SLO、质量漂移、事件响应和持续 Eval 都应进入交付边界。

这类项目通常适合“固定项目费或阶段交付费 + Managed Service”。建设费覆盖系统落地，持续服务费覆盖知识维护、模型切换、评估回归、异常处理、成本优化和小版本迭代。

第四层：复杂企业 AI 系统，交付跨流程、跨组织的运行机制

最高一层不是简单增加更多 Agent，而是形成复杂系统。

多个 Agent、Workflow、模型和数据域共享身份、权限、评估、可观测性和成本治理；它们跨部门协同，部分动作会改变库存、价格、合同、客户承诺或生产计划。系统还要面对多地区、多租户、高可用、灾备、安全审计、模型路由和供应商切换。

这时，交付对象已经从单一应用升级为企业 AI 能力体系。FDE 不只写代码和接接口，还要与业务、IT、产品、数据、安全和管理层共同重构流程、责任、预算与运营节奏。

复杂系统几乎不适合在信息不足时直接报一个永不变化的总价。更健康的方式是分阶段定价：先付 Discovery 与总体架构费，用真实证据锁定范围；再按能力域或里程碑实施；生产阶段采用平台费、Retainer 或 Managed Service；对少数能够清楚归因的业务结果，再加入 Gain Share。

层级越高，交付对象越从功能转向系统，责任也越从上线延伸到持续运营。图片：FDE中国社区自制。

判断层级，不要只数功能，要看五种复杂度

一个项目属于哪一层，不能只看需求清单有多长。更可靠的方法，是同时判断五种复杂度。

第一是业务复杂度：任务是否有大量例外，错误会造成多大影响，结果能否被快速验证。

第二是系统复杂度：需要连接多少系统，接口是否稳定，是否涉及读写、事务、补偿与遗留系统。

第三是智能复杂度：是固定流程、单 Agent 动态规划，还是多个 Agent 与模型协同；上下文、记忆和工具选择有多大不确定性。

第四是生产复杂度：并发、延迟、可用性、可观测性、回滚、灾备和成本上限要求有多高。

第五是组织复杂度：涉及多少部门，数据和流程由谁拥有，谁推动采用，谁有权批准、暂停和承担业务结果。

功能数量相同，只要这五项中的两三项明显上升，交付层级和报价都可能变化。一个内部文案助手和一个能修改订单的销售 Agent，即使页面一样，也绝不能用同一套责任和价格衡量。

功能只是表层，业务、系统、智能、生产与组织共同决定真实交付成本。图片：FDE中国社区自制。

能力分层之后，再选择六种收费工具

常见收费方式仍然可以归为六类，但它们是工具，不是起点。

人天或 T&M 适合范围尚未稳定的 Discovery、架构诊断和遗留系统摸底。它便于覆盖不确定性，但要设置每周产出、预算上限和阶段退出条件。

固定项目价适合边界清楚的 Workflow 和窄范围能力。合同必须同时写交付物、验收指标与变更机制，避免把未知接口和脏数据藏进一个看似精确的总价。

Skill、Workflow、Agent 或 Connector 资产费，适合已经形成可复用能力的团队。要写清源代码、许可、实例、版本、客户数据、专属规则和退出迁移的权利。

按调用量或 Task 收费，适合已经进入生产的高频标准化流程。必须定义一次任务从哪里开始、到哪里结束，失败重试、人工接管和第三方费用如何计算。

订阅或 Managed Service 适合需要长期监控、评估、知识维护、模型切换和持续改进的生产系统。月费背后要有服务目录、SLO、响应时间和迭代额度，不能只写“长期维护”。

Outcome Based 适合结果可量化、主要变量可控制、验证周期较短的项目。客服解决、票据处理、合同审查等通常比品牌、战略和复杂销售更容易定义结果。

市场上的产品计费也体现了这条演进路径。截至 2026 年 9 月，AWS AgentCore[2]按运行资源、查询和 API 调用等消耗收费；Salesforce Agentforce[3]把 Action 映射为 Flex Credits；Intercom Fin[4]则把 Resolution 等定义为可计费 Outcome。底层资源、执行动作与业务结果，本来就是不同的价值层。

我更推荐的组合公式：Delivery + Asset + Run + Outcome

对于真正要进入生产的 FDE 项目，可以把总报价拆成四层。

第一层是 Delivery Fee，购买发现、架构、集成、评估、部署和试点，回答“这项能力能否被交付”。

第二层是 AI Asset Fee，购买 Skill、Workflow、Agent、Connector、Ontology 或行业模板，回答“项目留下了什么可复用资产”。

第三层是 Run Fee，按月、按 Agent 或按任务支付模型、基础设施、监控、维护和持续优化，回答“系统能否稳定运行”。

第四层是 Outcome Fee，按可核验的成本节约、周期缩短、质量提升或收入增量分享价值，回答“结果发生后如何分配收益”。

公式很简单：

FDE Revenue = Delivery + Asset + Run + Outcome

四层不必每个项目全部使用。Workflow 可以是 Delivery + Asset；生产 Agent 可以是 Delivery + Run；生产级流程系统通常再加 Managed Service；复杂企业 AI 系统才更适合 Retainer、平台费和部分 Outcome 的组合。

基础费用覆盖可控成本，资产费奖励复用，运行费承担持续责任，效果费分享增量价值。图片：FDE中国社区自制。

不建议纯效果对赌

效果收费的上限最高，但 Outcome 很少由 AI 项目单独决定。

销售额变化可能同时受产品、价格、渠道、市场和销售执行影响；客服成本变化也可能来自业务量、排班、服务政策与外包合同。如果服务商不能控制这些变量，却要承担全部结果风险，“没效果不收费”就等于替客户承保经营风险。

更合理的是 Base Fee + Success Fee。基础费用覆盖可控的发现、实施与运营成本，效果费用分享双方共同创造的增量价值。

引入效果费前至少要满足三项条件：有双方认可的历史基线和取数口径；服务商能够控制主要流程，外部变量可以剔除；一到三个月内能够看到结果并解决争议。能做 A/B 测试就不要只做前后对比，不能随机对照时，也应设置对照组、趋势校正或双方认可的财务口径。

先定能力层级，再组合报价；层级越高，持续服务与价值分享越重要。

最后：价格应该跟着责任升级

客户真正愿意长期付钱的，不是模型、Prompt 或 Agent 这些名词本身，而是更低的成本、更快的流程、更少的错误和一套能够持续运行的业务能力。

FDE 报价的关键，也不是找到一种听起来更先进的收费方式。

先说清楚交付能力处在哪一层，再说清楚谁控制哪些变量、系统如何验收、上线后由谁负责，最后才选择人天、固定价、资产费、运行费和效果费的组合。

从 Workflow 到复杂系统，价格上升的本质从来不是代码更多。

而是交付团队承担了更完整的生产责任，也帮助客户获得了更接近业务结果的能力。

关注 FDE前线，我们会继续拆解企业 AI 从报价、交付到生产运营的真实方法。
