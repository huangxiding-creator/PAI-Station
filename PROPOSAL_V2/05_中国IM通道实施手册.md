# 第 5 章 中国 IM 通道实施手册（逐平台操作级）

> 目标：把 openhuman 的"17 通道全是西式应用"改造成中国职场四大 IM 全覆盖。每个通道给出：接入方式选型对比、注册配置步骤（照做即可）、代码骨架、风险控制、验收标准。

## 5.1 四通道总览

| 通道 | 接入方式 | 公网暴露 | 能力 | 定位 |
|---|---|---|---|---|
| 飞书 | lark-oapi WS 长连接 | 不需要 | 收发消息/文件/卡片/日程 | 全功能主通道（先做） |
| 钉钉 | dingtalk-stream | 不需要 | 收发消息/文件 | 全功能 |
| 企业微信 | 自建应用（REST+回调） | 需要（或内网穿透） | 收发消息/审批卡片 | 主通道+审批确认入口 |
| 微信 | 纯视觉只读 | 不需要 | 只读感知（截图→VLM） | 感知通道，绝不自动化 |

## 5.2 飞书通道（lark-oapi，WebSocket 模式）

**为什么选 WS 模式**：飞书开放平台提供事件订阅两种模式——Webhook 回调（需要公网 IP/域名/备案）与长连接（本机直连，无需任何公网暴露）。个人笔记本场景 WS 是唯一顺滑解。

**配置步骤（照做）**：
1. open.feishu.cn → 创建企业自建应用（个人可注册免费版飞书组织）；
2. 权限管理开通：`im:message`、`im:message.group_at_msg`、`im:resource`（下载消息中的文件）；
3. 事件与回调 → 订阅方式选"使用长连接接收事件"→ 订阅 `im.message.receive_v1`；
4. 凭证与基础信息 → 拿到 App ID / App Secret 填入 `config/feishu.ini`；
5. 版本管理与发布 → 应用上线（自建应用免审）；
6. 把 PAI-Station 机器人拉进需要的群或加为单聊联系人。

**代码骨架**：
```python
import lark_oapi as lark
def on_message(ctx, conf, event):        # im.message.receive_v1
    text = extract_text(event.message)   # 富文本/图片消息分别处理
    task = classify(text)                # glm-4-flash 系统1分类
    enqueue(task, reply_to=event.message.chat_id)
client = lark.ws.Client(APP_ID, APP_SECRET,
                        event_handler=dispatcher, log_level=lark.LogLevel.INFO)
client.start()                            # 阻塞线程，断线自动重连
```
**验收**：群里 @ 机器人"整理今日会议要点"→ 60 秒内回卡片，附出处文件。

## 5.3 钉钉通道（dingtalk-stream）

**选型**：钉钉 Stream 模式同样免公网（对比 HTTP 回调模式）。开放平台 create.oa.dingtalk.com → 应用开发 → 消息推送选 Stream 模式 → 拿 Client ID/Secret → 订阅企业内部机器人消息事件。代码骨架与飞书同构（两个通道共用 `channels/base.py` 抽象：on_message/on_confirm/send_file）。
**验收**：单聊发文档→收到摘要回复；断网 30 秒恢复后消息不丢（Stream 补投）。

## 5.4 企业微信通道（自建应用）

**步骤**：
1. work.weixin.qq.com 注册企业（个人可注册，无需对公）→ 应用管理 → 创建自建应用"PAI-Station"；
2. 拿 CorpID + Secret + AgentID 填 `config/wecom.ini`；
3. 接收消息：两方案——A. 回调模式（需公网，用 cpolar/natapp 内网穿透或家宽公网）；B. **轮询模式（默认）**：定时拉取通讯录同步与日程变化，机器人主动发消息（webhook 或应用消息 API），用户指令经"客户消息"接口被动回复。默认 B 起步（零公网），进阶用户开 A；
4. 主动推送：应用消息 API `message/send`（markdown 卡片）——这就是主动服务的推送通道，也是双环学习审批的确认入口。

**审批卡片（创新点）**：双环学习的重大变更、Tool Guard 危险命令确认，都发企微 markdown 卡片给用户，回复"同意/拒绝"完成闭环——把审批搬到用户最常看的地方。
**验收**：主动推送 P90 到达 ≤5 秒；审批回复在 24h 内回收率 ≥80%。

## 5.5 微信通道（纯视觉只读——本项目最重要的安全决策）

**背景**：微信没有个人可用的开放接口。历史方案全线阵亡：网页版微信（2017 年起大规模封禁）、ItChat/itchat（同源，失效）、协议逆向（强风险）、Xposed/Hook（root/越狱+封号）。**个人微信自动化在微信官方明确禁止范围**——任何 Hook 方案对用户都是封号赌博，作为产品不可接受。

**我们的方案：纯视觉只读**
```
微信窗口（PC 版）→ mss 定时/事件截图 → 黑名单过滤 → GLM-4V-Flash 结构化识别
→ {发送人/内容摘要/时间/情绪信号} → 作为记忆事件入 memory.db
→ 触发器：识别到"领导@你 要材料"→ 主动层评估 → 企微/飞书推送提醒
```
四条铁律（写死在代码，INI 改不了）：
1. **只截图，零注入**——不 Hook、不模拟点击、不发消息、不加好友；
2. **只读公开界面**——密码框/支付页黑名单整窗丢弃；
3. **原文不存**——只存 VLM 产出的摘要与实体，原始截图 10 分钟滚动销毁；
4. **默认关闭**——首次开启弹窗明示风险与用途，用户主动确认才启用。

**验收**：连续挂机 30 天微信零异常（无风控提示、无强制下线）；识别准确率抽检 ≥85%；原始截图文件系统断言：10 分钟后缓冲目录为空。

## 5.6 通道抽象层（channels/base.py）

```python
class Channel(ABC):
    @abstractmethod
    def send_text(self, to, text): ...
    @abstractmethod
    def send_file(self, to, path): ...
    @abstractmethod
    def send_confirm(self, to, question, options) -> confirm_id: ...
    def listen(self): ...                      # 各自实现 WS/轮询/视觉
    def register_router(self, fn): ...         # 指令路由：classify→技能
```
新通道（QQ/Telegram）只需继承 Channel 实现 4 个方法——为社区贡献通道留好缝。
