## Q1 归因链路：wxacode.getUnlimited scene 带参 + 扫码解析 + tracking 表

### 1.1 官方接口契约（已实读官方文档）

**核心接口**：`getUnlimitedQRCode`（POST `https://api.weixin.qq.com/wxa/getwxacodeunlimit`），"获取不限制的小程序码"，适用于需要的码数量极多的业务场景——海报裂变每张海报一个邀请人专属码，正是该接口的目标场景。

- **scene 参数**：最大 **32 个可见字符**；仅支持数字、大小写英文以及 `!#$&'()*+,/:;=?@-._~`；**不支持 %**（故不能 urlencode 中文，参数必须用短ID/短码）。
- **page 参数**：默认主页面；**不能带参数**（query 参数只能放 scene 里）；不能带前导 `/`；必须本小程序已发布的页面（`check_path` 默认 true；false 可用于未发布页但页面总数上限 60000）。
- **env_version**：要打开的小程序版本，release（默认）/trial/develop。
- **width**：二维码宽度，默认 **430px**，范围 280-1280。海报印刷位建议 600-800px 保证扫得动。
- **数量与频率**：接口 B 码数量**无限制**（对比接口 A/C 合计 100,000 个上限）；调用频率 5000 次/分钟，**官方建议预生成**（避免每用户实时生成触发限频）。
- **scene 到达方式**：scene 值会作为 query 参数传给指定 page；**开发工具模拟编译时需手动 encodeURIComponent**。
- **关键错误码**：40129 scene 非法；41030 page 不存在/未发布；40169 长度非法；45009 调用次数超限；47001 body 非 JSON；89300 无效 signature（小程序未发布时）。

证据：
1. 微信官方文档《获取不限制的小程序码 wxacode.getUnlimited》 https://developers.weixin.qq.com/miniprogram/dev/api-backend/open-api/qr-code/wxacode.getUnlimited.html — **可信度 1.0**（本机实读全文，参数表逐条核对）
2. 微信官方文档《小程序码/二维码总览》（接口A/B/C选型、10万上限、5000次/分、预生成建议） https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/qr-code.html — **可信度 1.0**（本机实读）
3. 微信开放文档服务端索引（getUnlimited 条目存在性交叉验证） https://developers.weixin.qq.com/miniprogram/dev/OpenApiDoc/qr-code/QRCode/getUnlimited.html — **可信度 0.95**

### 1.2 report_id + 邀请人ID 的 scene 打包标准做法

scene 32 字符预算下的标准玩法（社区一致实践）：

- **直拼短参数**：`r=Ab3xK9&i=U8mQ2z`（r=研报短ID，i=邀请人短ID），约 18 字符，余量充足；分隔符 `&`/`=`/`-` 均在合法字符集内。
- **溢出兜底=短码映射**：参数放不进 32 字符时，服务端先落库 `scene_code → {report_id, inviter_uid, channel, poster_version}`，scene 只存短码（如 `s=Xk29fA`），扫码端查映射表还原——同时天然成为 tracking 落地点。此模式在 CSDN/掘金/阿里云开发者社区的 getUnlimited 实战文章中反复出现。
- **ID 必须短化**：openid 28 字符直接塞必爆，须用自增 uid/Base62 短ID。

证据：
4. CSDN《小程序码 getUnlimited scene 参数实战》类文章（搜索摘要引用，完整路径未捕获，标题+域名可复现检索） https://www.csdn.net — **可信度 0.6**（技术社区，与官方契约一致）
5. 阿里云开发者社区 scene 短码映射实践文 https://developer.aliyun.com — **可信度 0.6**
6. SegmentFault/掘金 onLoad 解析 scene 的标准代码片段（decodeURIComponent + split('&') + split('=')） https://juejin.cn / https://segmentfault.com — **可信度 0.65**

### 1.3 扫码进入页 onLoad/onShow 解析与参数丢失兜底

标准解析链（社区标准写法 + 官方 query 传递规则）：

```js
// onLoad(options)：scene 以 query 参数到达，需 decodeURIComponent 后自行解析
onLoad(options) {
  const scene = decodeURIComponent(options.scene || '')  // 'r=Ab3xK9&i=U8mQ2z'
  const params = {}
  scene.split('&').forEach(kv => {
    const [k, v] = kv.split('=')
    if (k) params[k] = v
  })
  // params.r → 研报ID；params.i → 邀请人ID
}
```

- 官方仅保证 scene 作为 query 传入；解析、校验、兜底全部自己写。
- **兜底三板斧**（社区实践汇总）：① scene 缺失/解析失败 → 降级为无邀请人进入（report_id 用页面默认值，inviter 置空，不做归因）；② onLoad 参数丢失（冷启动被系统回收等边缘case）→ 落地页把 scene 写入本地缓存，onShow 再校验一次；③ scene 走短码映射时，映射查不到 → 同①降级，不阻塞用户看免费部分（免费内容兜底优先于归因，转化损失>归因损失）。
- 开发者工具模拟扫码必须手动 `encodeURIComponent`，真机自动——这是最常见的"本地好好的真机解析失败"坑。

证据：
7. 掘金/CSDN scene 解析与踩坑文章（同4/6，标准片段一致收敛） — **可信度 0.65**
8. 神策数据小程序渠道追踪文档（channel+scene 归因埋点模型） https://www.sensorsdata.cn — **可信度 0.7**（厂商文档，模型是行业通用）

### 1.4 分享 tracking 常见表设计（综合社区实践，非官方规范）

| 表 | 关键字段 | 作用 |
|---|---|---|
| `poster_code`（码映射表） | scene_code, report_id, inviter_uid, poster_version, created_at | scene短码→业务参数还原；预生成码池 |
| `share_event`（分享事件） | share_id, uid, report_id, channel(海报/会话/朋友圈), poster_version, ts | 谁在何时分享了哪份研报的哪版海报 |
| `invite_relation`（邀请关系） | inviter_uid, invitee_uid, report_id, scene_code, status(扫码/注册/解锁/付费), ts | 邀请归因主表，首触归因(first-touch) |
| `scan_visit`（扫码访问） | scene_code, openid/uid, entry_page, ts | 漏斗第一环：曝光→扫码落地的度量 |

> 说明：微信官方不规定 tracking 表结构；上表为 CSDN/掘金实战文与神策归因模型的综合收敛，可信度 0.65（设计参考而非硬证据）。K因子（Q5）所需的"人均邀请数×邀请转化率"可直接由 invite_relation 聚合。

## Q2 海报生成技术三路线对比

### 2.1 路线A：服务端生成（PIL / Node canvas / puppeteer 截图）

- 做法：服务端按模板渲染 → 返回**图片 URL**（CDN），小程序 `<image>` 直接加载，长按保存/分享。
- 优点：**渲染结果与设备无关**（千机一面）、清晰度可控（高分辨率导出，无 canvas 缩放模糊）、模板改动**不发版**、小程序码可预生成缓存、个性化字段（邀请人昵称/头像）服务端拼装零成本。
- 缺点：服务器 CPU/内存开销（puppeteer 截图尤重）、字体文件管理、长图内存；需自建或买 CDN。
- 大厂实践：知乎专栏《动手打造一款 canvas 排版引擎》（2022-02）明确服务端路线=「写一个 node 服务，用 puppeteer 访问提前写好的网页来截图」——复杂排版引擎跑在服务端是重内容平台的收敛选择。https://zhuanlan.zhihu.com — **可信度 0.7**

### 2.2 路线B：小程序端 canvas（官方 wxml-to-canvas / 开源 Painter）

**wxml-to-canvas（官方扩展组件，已实读官方文档）**
- npm 安装引入；用**静态 wxml + wxss 模板**渲染到 canvas，`renderToCanvas` → `canvasToTempFilePath` 导出图片，支持 fileType（jpg/png）与 quality。
- 能力边界：仅支持 **view / text / image** 三种标签、**仅 flex 布局**——不是完整 CSS 子集，复杂版式做不了。
- 优点：官方维护、无服务器成本、实时生成（邀请人昵称/头像实时变化）、数据不出端。
- 缺点：布局受限、低版本基础库兼容坑、多机型 dpr 缩放需自己按 2x/3x 处理否则模糊。
- 证据：微信官方文档《wxml-to-canvas》 https://developers.weixin.qq.com/miniprogram/dev/extended/component-plus/wxml-to-canvas.html — **可信度 1.0**（本机实读）

**Painter（酷家乐开源，JSON 数据驱动）**
- JSON 描述海报 → 渲染 canvas 导出；支持更丰富的布局/圆角/渐变等。
- 51CTO《前端生成海报图技术选型与问题解决》（2024-06-06）对比结论：**wxml-to-canvas 使用相对较简单**（引入库+传 wxml 与宽高即可），**Painter 功能更强大但上手更复杂**——是社区公认的取舍线。https://www.51cto.com （搜索摘要引用，文章完整路径未捕获） — **可信度 0.6**
- GitHub 仓库：https://github.com/Kujiale-Mobile/Painter — **本机 fetch degraded**（域名校验拦截，未实读 star/更新时间；该库为小程序海报事实标准之一，社区文章交叉印证） — **可信度 0.6，标注 degraded**

### 2.3 路线C：云函数生成

本质仍是服务端生成（node canvas / puppeteer 跑在微信云开发函数里），差异在部署形态：免运维、与 `wxacode.getUnlimited`（cloudapi 从云函数内网调用免 access_token 管理）天然亲和；缺点：冷启动延迟、内存/时长限制（puppeteer 类重渲染易顶格）、按调用量计费在裂变峰值期成本反超自备服务器。

### 2.4 三路线对比表

| 维度 | A 服务端(PIL/node-canvas/puppeteer) | B 端侧 wxml-to-canvas / Painter | C 云函数 |
|---|---|---|---|
| 加载速度 | ★★★ 预生成+CDN图片URL直出 | ★★ 现算1-3s，低端机更慢 | ★★ 冷启动+现算 |
| 清晰度 | ★★★ 服务端高分辨率导出 | ★★ 需手动处理dpr，机型差异 | ★★★ 同A |
| 维护成本 | ★★ 模板改服务端即生效，但需管服务器/字体 | ★★ 官方库低（wxml-to-canvas）/开源库看社区（Painter） | ★★★ 免运维 |
| 布局能力 | ★★★ 完整(CSS/HTML) | ★ wxml-to-canvas仅3标签+flex；Painter较强 | ★★★ 同A |
| 个性化实时性 | ★★ 需生成后上传CDN | ★★★ 实时 | ★★ |

**知名小程序用哪条**：重内容/大流量平台收敛于**服务端**（知乎排版引擎文章为证）；中小团队与强实时个性化场景主流用**端侧 wxml-to-canvas/Painter**（51CTO选型文与大量 CSDN 实战文为证）。两者常混用：模板骨架服务端预渲染 + 用户头像昵称端侧合成。

**对研报商城的推荐结论**：研报海报 = 模板固定（封面+数据摘要+码+品牌条）+ 小程序码按邀请人预生成 + 传播主战场在朋友圈长按识别 → **首选路线A（服务端生成，图片URL直出）**，码走预生成池（官方明确建议），CDN 出图；端侧 wxml-to-canvas 仅在需要"用户实时换头像昵称"的轻量场景补充。

### 3.2 合规边界：利益诱导分享 vs 自愿分享激励

**红线（明确禁止）**：
- 《微信公众平台运营规范》3.3 诱导分享：禁止**强制**或**利益诱导**分享朋友圈（奖励含现金、实物、红包等）；处罚阶梯：删文→删粉→封禁分享能力→封号（四级）。https://developers.weixin.qq.com （官方规范入口） — **可信度 0.9**
- 微信安全中心 2019《关于利诱分享朋友圈打卡的处理公告》：「打卡返现」类被批量处理——**晒单返现/打卡返现金=高危**。 — **可信度 0.85**
- 多级分销（≥2级返佣）事实上必封（新世相二级、网易三级均当日处理）。
- 判例佐证：售卖「诱导分享裂变程序+防封系统」被法院认定不正当竞争——平台态度司法化。 — **可信度 0.7**

**安全区（自愿+虚拟权益）**：
- 激励物为**产品内虚拟权益**（免费解锁研报章节/阅读券/会员体验），非现金非实物；
- 分享是**解锁路径之一而非唯一路径**（用户也可付费直接解锁）；
- 不强制发朋友圈、不要求截图验证、不搞打卡返现；
- 微信读书「组队抽无限卡」多年在役是该边界的最佳活样本。

**对研报商城的直接结论**：「邀请解锁免费章节」（邀请2人各扫码解锁→自己得完整免费部分/优惠券）+「组队阅读研报」（3人成队全队各得一份报告阅读权）双玩法均落在安全区；**砍价/晒单返现/多级分销不碰**。
