# 国际工程项目进度计划的六重定位

原创 毕立红 2026-09-21 08:58 北京

设计咨询走出去实践及典型案例

作者：毕立红 BI LIHONG

前某跨国公司全球项目执行中心项目计划部门经理

引 言：

一张横道图背后的权力结构

在国际工程项目的语境里，进度计划（Programme / Schedule）从来不是一张贴在墙上的横道图。

翻开 FIDIC 银皮书、黄皮书或红皮书的任何一本，你会发现"Programme"是单独成条的合同义务：承包人要在开工后若干天内提交，工程师要在若干天内批复，之后每一版修订都要重新走一遍这个流程。合同之所以把它写得这么重，是因为进度计划承担着一个不可替代的角色——它是合同义务在时间轴上的投影，是唯一一份同时被业主、工程师、总包、分包、供应商共同引用，又同时约束所有人的文件。

报价决定能不能拿到项目，进度计划决定这个项目是赚钱还是赔钱。

很多项目的失控，表面看是"工期延误"，实质上是进度计划从一开始就没有被摆到正确的位置上：它被视为计划工程师个人的技术工作、被视为投标时的附赠品、被视为业主要求的一份格式文件。等到现场出了事，才发现没有一张图能说清"谁答应了什么、什么时候答应、为什么晚了、晚了是谁的错"。

因此，讨论进度计划，首先要讨论它的定位。

在国际工程项目的完整治理链条里，进度计划至少承担六重定位：契约、界面、范围、流程、监控、证据。它们彼此咬合，缺一不可。

一、契约：

进度计划是合同的"时间宪法"

1. 三类节点，构成合同的骨架

一份有契约效力的进度计划，节点不是随便挑的。它至少要完整承载三类节点：

（1）合同节点（Contractual Milestones）

即合同明文规定的日期：开工日（Commencement Date）、竣工日（Time for Completion）、区段竣工（Sectional Completion）、移交（Taking-Over）、缺陷责任期起算与终止、性能考核窗口期等。这类节点的特征是：一旦失守，直接触发合同责任——最常见的是误期损害赔偿（Liquidated Damages, LDs），通常按日计罚、设有上限（常见为合同额的 5%~10%）。

因此在计划中，这类节点必须做到三件事：单独标识（如P6软件当中的 Activity Code 或 Milestone 分类）、可追溯到合同条款号、与罚则金额建立对照表。计划工程师要能随口回答："这一条节点晚了十天，合同代价是多少。"

（2）收付款节点（Payment Milestones）

国际工程的现金流，本质上挂在计划上。

里程碑付款类项目：每一个付款节点就是一个必须被工程实体或文件成果支撑的里程碑，前提交付物（Deliverable）不完成，付款不启动。

进度款计量类项目：每月的 Interim Payment Certificate 依赖于进度测量值，而进度测量值来源于计划的权重体系。

还有质保金释放（Retention Release）、履约保函/预付款保函的到期与展期、延期付款利息的起算等，全部与计划节点绑定。

一句话：计划的节点顺序，就是现金流的时间表。 把长周期、高权重的收款节点往后挪一个月，财务成本立刻体现；把需要业主配合的前置条件漏掉，回款风险立刻产生。

（3）文件节点（Documentary Milestones）

国际工程最容易被低估的一类节点，是"纸面节点"：图纸提交（Submission）、业主/工程师批复（Approval）、许可批文（Permit / Approval from Authority）、材料报批（Material Approval）、施工方案报批、第三方审查、竣工资料（As-Built / O&M Manuals）等。

合同里通常明确写有批复时限，例如"工程师应在收到后 21 天内批复"。这个 21 天不是背景噪声，它是工期的一部分。一份合格的计划必须把"提交—批复—返回"的完整循环建成活动，并且把业主方/第三方作为责任方显式表达出来，而不是笼统地用一个"等待审批"的横道蒙过去。

如下案例，某国际工程项目P6计划的WBS前面几个一级分类，主要就是合同节点、界面、关键日期、文件交付等，这不只是一份进度计划，而是项目合同中各方义务的“契约化”体现。

2. 基准计划：批准即契约化

进度计划的契约属性，集中体现在"基准计划（Baseline）"这一动作上。

基准未批准之前，计划是承包人的内部设想；

基准一经批准，它与合同文件、技术规范、工程量清单一起，构成双方共同的"时间宪法"。

由此产生两条铁律：

改基准 = 改合同。 任何对关键节点、关键路径、合同工期的实质性调整，都不能由计划工程师在软件里悄悄完成，必须走变更（Variation）或工期延长（Extension of Time, EOT）程序，形成书面记录。

保留每一版。 旧版本不能覆盖。每版计划要有版本号、数据日期（Data Date）、修订说明、与上一版的差异对比表。这些版本序列本身就是日后主张权利的证据链。

实操建议：开工初期做一张《合同日期清单》——把合同、补遗、会议纪要、业主指令中出现的所有日期与期限（开工、交地、批复时限、通知时限、移交、考核、保函到期……）逐条摘出，注明条款出处，再逐条映射到计划节点。这张表是计划与合同之间的"接线图"，也是项目上唯一不该由计划工程师单独完成、必须由合同经理会签的文件。

在我看来，一面好镜子（好的项目计划基准Baseline）必须具备如下因素：

1) 范围完整（Full Scope）

该项目计划基准必须完整涵盖项目的交付范围。

2) 结构清晰(Clear Structure)

该项目计划基准必须有完整的结构，逻辑清晰、主次分明。

3) 分工明确（Specified DOW(Division of Work）

大型工程项目通常是由多方合作完成的，比如工程项目的EPC联合体（Consortium）、设计院（DI）、主供货商、子供货商、监理单位以及施工方等等。

项目分工，主要分为外部分工和内部分工。这里所说的分工，是站在EPC的角度或者主供货商的角度，组织以内包括内部联合体、内部职能部门的叫内部，组织以外的合作方（甲方、设计院、乙方等）叫作外部。

4) 贯穿始终（Fixed Baseline）

一个好的项目计划基准，应该是一盏或者一路的指路明灯，照亮了到达终点的方向。而不是只看眼前，不看长远。

5) 充分体现项目特点

项目计划基准，要尤其单独体现每个项目的独特性。而不是随便找一个旧项目的模板，旧不像旧、新不像新。项目之所以成为项目，因为项目的特征之一就是独特性。所有的项目都是独一无二的，可谓前不见古人、后不见来者。即便有可参考项目，也只是项目的部分内容具有类似性，比如设备性能和参数类似、项目地点和客户类似、项目融资结构类似等等。

6) 可执行性强

计划之所以能够成为团队的指南针，在于其指出了实现了项目目标的方向。其潜台词就是，只要整个团队严格执行计划，就能实现项目目标。

而在实践当中，因为种种原因，尤其被大家津津乐道的所谓“计划赶不上变化”为由，忽视了严格执行计划的重要性。导致计划不能成为指南针，反而被迫不断调整，“计划”变成了“记录”。

7) 充分考虑项目风险和机会（Risk and Opportunity）

具体到项目管理当中，在项目初期，组织项目团队提前针对项目的风险和机会进行识别和分类，并提前制定风险缓解措施，这些措施的其中之一，就是提前预留适当的风险缓解周期和成本预算；实际操作中，在进度管理方面，是通过预留额外的项目浮时（float）来实现，在成本管理方面，是通过预留额外的风险准备金（Risk Provision）来实现。

浮时（float）是项目进度风险的预留储备，用以对抗项目执行过程中出现的各种不可预见、不可避免、不可控制（不可抗力三要素）的各类事件。

所以，我们在项目管理当中，用Float来对抗各种风险。风险越大，我们预留的Float就越多......

二、界面分工：

活还没干，先把"锅"（Responsibility）分好

进度计划的第二重定位，是责任分工的可视化载体。国际工程里有个略带黑色幽默的说法：计划的第一价值不是"安排活"，而是"分锅"。这话不刻薄，是经验。

放在国内的人情世故语境下，很多人很难理解，这就体现了跨文化差异。国人做项目往往讲究先情后事，尤其在业主面前，总觉得活还没开始干，就先“分锅”，会让业主不高兴。然而放在国际语境下，你先“分锅”，业主反而踏实，至少他知道你是拎得清的，把项目交给你，放心。

1. DOW / 分工矩阵是什么

DOW（Division of Works，工作分工）或 Scope Matrix / Responsibility Matrix，是把全部工程内容按"谁设计、谁供货、谁施工、谁调试、谁负责接口"进行切分的一张矩阵。

它通常覆盖的界面类型有三类：

组织界面：业主、PM/EPCM、设计方、总包、各专业分包、设备供应商、当地政府与公用事业公司之间的责任边界；

物理界面：土建与安装的交接点（基础、预埋件、灌浆）、管道与设备法兰分界、电气单线图的分界点、控制信号的接口协议；

时间界面：谁在什么时点，把什么状态的成果移交给谁——场地移交、图纸移交、设备到货移交、单机调试向联调移交、运维移交。

国际工程里常见的"锅"，几乎全部出在这三类界面的缝隙里：螺栓垫片由供货方还是安装方提供？设备二次灌浆谁做？临时水电谁接谁付？调试用耗材谁采购？垃圾清运谁负责？深化设计（Shop Drawing / Detail Design）由谁出？到场卸货谁来吊？

这些问题如果不在计划里体现为明确的、双方共用的交接里程碑，现场一定会变成扯皮现场。

而在实践当中，我们通常用P6当中的作业代码Activity Code 来标识每个作业的分工及DOW。

2. 计划如何表达界面

成熟的做法是四步：

建立界面清单（Interface Register）：每条界面一个 ID，写明双方主体、交付内容、交付标准、交付时点、责任人。

把界面做成双向里程碑：移交方计划里有"移交"（Handover / Provide），接收方计划里有"接收并确认"（Receive & Accept），两者使用同一个界面 ID，日期一一对应。

把界面日期纳入双方计划会审：分包计划、供货商制造计划（Manufacturing Schedule）必须与主计划的界面节点对齐，不一致处即为待办。

对未定界面挂"假设与待定项"：任何 DOW 尚未谈定的内容，在计划中以明确的假设条件（Assumption）或 TBD 活动存在，并设跟踪责任人。绝不能默认"反正到时候再说"——到时候一定是最忙的时候。

一句话总结：界面不清，则责任不清；责任不清，则工期与费用都无从说起。 计划在这里的作用，是把"锅"在开工之前分完，并让所有人亲眼看见自己领走了哪一只。

三、WBS 即范围：

做什么，更要写清不做什么

进度计划的第三重定位，是范围（Scope）的结构化表达。WBS（Work Breakdown Structure）不是画图时的分组标签，它就是范围本身。

1. WBS 是范围的投影

一个合格的项目 WBS，应当是范围说明书 / 合同工作范围条款的逐层展开。检验标准很朴素：把 WBS 打印出来给合同经理看，他能不能从中找出全部应做的工作，以及全部明确排除的工作？

这意味着两件事：

做什么（In-Scope）：必须完整覆盖合同义务，包括容易被遗漏的"软工作"——报批报建、第三方审查、培训、备品备件、竣工资料、性能考核配合、缺陷责任期服务等。

不做什么（Exclusions）：同样要以 WBS 词典或范围说明的形式写明。国际工程中，排除项往往比包含项更容易引发争议。

2. WBS 词典：防范围蔓延的第一道防线

WBS 的每一个末级工作包（Work Package），都应配一段简短的 WBS 词典：工作内容的文字描述、交付物、验收标准、责任单位、关联合同条目、计价方式。

这份词典的价值，在于它是范围蔓延（Scope Creep）的拦阻索。现场最容易发生的场景是：业主要求"顺手加一下"，量不大，但合同无此项、WBS 无此包、价款不含此内容。此时只要翻开 WBS 词典——"不在本工作包内，需走变更"——判断就完成了一半。

3. WBS 是项目管理的公共主键

WBS 之所以重要，还因为它是各管理维度之间唯一可靠的连接键：

与 CBS（费用分解结构）对齐 → 进度与成本联动，可算挣值（EV）、可算 S 曲线；

与 OBS（组织分解结构）对齐 → 每项工作有明确责任单位；

与 PBS（物理/交付物分解结构）对齐 → 与现场的实体部位、系统、区域对应，便于分包与验收；

与质量（ITP）、风险、安全、文控（文件编号）对齐 → 所有管理记录可归集到同一工作包。

若 WBS 与这些维度不对齐，项目就会出现经典病灶："计划里有这活，但预算里没这笔钱""现场干了活，但找不到对应的验收记录"。

4. 颗粒度：够用即可

WBS 分解遵循的原则常表述为 8/80 规则或 80 小时原则：单个工作包的工期与工作量既不能大到无法控制（一般不超过一个报告周期），也不能小到管理成本高于收益。对施工类项目，通常分解到"分项工程 × 区域 × 工序"层级即可作为执行层。

最后给一条反向校验法：拿 WBS 与合同工程量清单（BOQ）做一次双向对撞——BOQ 里有钱无活的，是漏项风险；WBS 里有活无钱的，是亏损风险。这一遍对撞，很多项目没做过，做过的基本都捡回了钱。

四、流程：

先干什么，后干什么

进度计划的第四重定位，是工程逻辑与审批流程的形式化表达。计划里的每一根箭线（逻辑关系），都应该能回答"为什么必须先干这个"。

1. 主线逻辑：设计—采购—施工—调试—移交

国际工程的通用主线为：

概念/基础设计（Basic Design）→ 详细设计（Detail Design）→ 业主审核（Client Review）→ 长周期设备采购（Long Lead Item）→ 施工安装 → 机械完工（Mechanical Completion）→ 预调试（Pre-commissioning）→ 调试/联动试车（Commissioning）→ 性能考核（Performance Test）→ 移交（Taking-Over）→ 缺陷责任期（Defect Notification Period）→ 最终验收。

这里面很关键的是中间环节的“业主审核（Client Review）”，在工期索赔中经常需要掰扯清楚项目延期到底是谁的原因，谁耽误了，耽误了多少天。给这类审核必须限定周期和时间，而且必须通过正式文件通知、记录。

这条主线在计划里不能是口号，而要落成三类逻辑：

工艺约束逻辑：先基础后安装、先地下后地上、先主管后支管、先单机后联动、先吹扫冲洗后试压、先送电后调试。这些是物理上无法颠倒的顺序。

信息依赖逻辑：设计图纸未批复不得用于施工（IFC，Issued for Construction）、材料未报批不得进场、方案未批准不得开工。信息不闭合，工序就不能开始。

资源与空间约束逻辑：同一区域两台吊车不能同时作业、同一批焊工不能同时出现在两个区域、试车期间不能交叉施工。这类约束通常靠P6软件中的资源曲线、人力直方图或区域约束来表达。

2. 长周期设备与快速跟进

国际工程的关键路径，往往由长周期设备（大型压缩机组、 reactors、变压器、定制非标设备、进口仪表系统等）决定，而不是由土建决定。因此成熟计划会把采购链条完整展开：询价 → 评标 → 定标 → 合同 → 厂家资料返回（Vendor Data）→ 制造 → 工厂验收（FAT）→ 发运（EXW/FOB/CIF/DDP 的交付界面）→ 清关 → 到场 → 开箱检验 → 安装 → 调试。

其中"厂家资料返回"是最常被压缩、也最常出事的一环：资料晚一周，详细设计跟着晚一周，基础图跟着晚，土建跟着晚。

为缩短工期而采用的快速跟进（Fast-Tracking）——图纸未全批就先开工、基础设计未完就先订设备——本质上是在用返工风险换工期。这类决策必须在计划里显式标出（例如标识为"假设批准"、设置返工缓冲），让管理层看见自己买了多少风险敞口。

3. 审批链路也是工序

在很多项目上，真正卡住工期的不是施工速度，而是审批链条。

一条典型的链路是：承包人提交（Submittal）→ 工程师审查（Review）→ 批复（Approval，含 Approved / Approved with Comments / Revise & Resubmit / Rejected 四种结果）→ 修改再提交 → 最终批准 → IFC → 施工 → 检验（ITP 见证点：H/W/R 点）→ 完工确认。

这条链路里的每一次循环都要占用日历时间，且大部分时间不在承包人的控制之下。因此，计划中必须有业主/工程师/第三方的工作条目（业主责任活动），并为其设定合同规定的时限。这也是日后主张"审批延误"的前提——你必须在计划里给了对方时间，才能说对方占用了你的时间。

4. 分层计划体系

国际工程通常采用分层计划体系（以下以电力行业为例，其他行业可能有所不同）：

实践当中常采用P6的网络版，通过多人协作实现。

五、过程监控：

进度是索赔的第一现场

进度计划的第五重定位，是过程监控与工期索赔的技术基础。前面四重定位做得再好，如果不更新、不分析、不主张，最后也只是废纸。

1. 监控的基础设施

更新节奏：月度更新是国际工程的标准动作，快节奏项目可双周更新；每次更新固定数据日期（Data Date），不得随意移动。

进度测量体系：按权重法（常见于 EPC，按设计/采购/施工/调试四阶段设定权重与里程碑）、实物量法（按工程量完成比例）或工序百分比法，形成可复核的完成百分比。权重体系应在项目初期就与业主书面确认——否则到了中期，双方会对"到底完成了 60% 还是 48%"争论不休。

曲线分析：S 曲线（计划/实际/挣值）、人力直方图、关键路径漂移、浮时（Total Float）消耗趋势。

2. 浮时归谁，是国际工程的经典问题

关键路径上的浮时为零，非关键路径上的浮时被消耗完，作业就转为关键。于是产生一个必答题：浮时是承包人的资源，还是项目的公共资源？

不同合同体系有不同处理，实务中较为常见的立场是：承包人在投标时应被视为已在其计划安排中用掉了可合理预期的浮时；但在业主延误事件发生后，判断责任的标准是"该事件是否消耗了本可用于吸收其他延误的浮时"。这条判断直接影响 EOT 的成立与否，因此必须在计划里把浮时算清楚、标出来、留版本，而不是藏在软件默认设置里。

尤其，如果可以的话，在总进度计划审批的时候，就写清楚进度计划中的浮时归属方，使用权限方。

3. 工期索赔（EOT）的技术路径

一次站得住脚的工期索赔，通常包含五个环节，环环相扣：

时效通知（Notice）：绝大多数合同（如 FIDIC 20.2 条）要求承包人在知悉或应知悉延误事件后的一定期限内（常见 28 天）发出通知。逾期通知，权利可能直接丧失。 这一条最容易被现场忽略，也最致命。

同期记录（Contemporaneous Records）：事件发生当时的记录，而不是事后补的回忆。日报、气象记录、影像、人员机械台账、往来函件、会议纪要、检验记录。

影响分析（Delay Analysis）：选定方法并说明适用性。常见方法有时间影响分析（TIA / Time Impact Analysis，把延误事件插入当期基准计划，比较前后竣工日期）、窗口分析（Windows Analysis，按时间切片逐段归责）、计划-实际对比（As-Planned vs As-Built）、影响事件剔除法（Collapsed As-Built / But-For）等。

量化结论：明确延误天数、影响的关键路径、是否涉及费用（ prolongation cost）、是否与自身延误同期发生。

佐证闭环：全部结论回到函件、图纸批复、指令、日志等原始记录，一一对应。

其中第三步与第五步，本质上都依赖计划本身的质量：计划逻辑关系不合理，影响分析就无法被采信——因为对方会证明"你这条路径本来就不该是关键路径"。

这就是"平时不好好做计划，索赔时没人信"的技术原因。

4. 同期延误与赶工

同期延误（Concurrent Delay）：业主责任事件与承包人责任事件在同一时段重叠。不同法域的处理差异很大（有的按比例分摊，有的不支持承包人索赔费用但给工期）。计划里必须能清晰标出两条延误的重叠区间。

赶工（Acceleration）：业主指令赶工，应作为变更计价；若业主拒绝承认延误、又要求按期完工，承包人被迫自行赶工并事后主张费用，则构成"推定赶工（Constructive Acceleration）"，举证难度大，必须以书面指令与书面异议为前提。

5. 每版更新都要能说清"为什么变"

更新不是机械地填完成百分比。每版计划应附修订说明：本期新增/删除了哪些活动、逻辑关系为何调整、进度测量为何变化、哪些是业主原因、哪些是自身原因、关键路径转移到哪里。

这份说明，是计划从"技术文件"上升为"管理文件"与"证据文件"的分水岭。所以我一直说，P6软件是项目管理软件，不是进度软件。

六、与文控关系：

不为打官司而来，却处处为打官司而准备

进度计划的第六重定位，是证据链的组织者。它与文控（Document Control）的关系，用一句话概括就是：不为打官司而来，然而处处为打官司而准备。

1. 计划与文控的三条主线

一条进度计划要能被举证，需要三条证据线同时成立：

函件线（Correspondence）：所有与工期相关的往来——业主指令（Employer's Instruction / SI）、变更令（Variation Order）、工程师批复、承包人的通知与索赔函、会议纪要（其中载明的决定与责任人）。

提交审批线（Submittal / Transmittal）：图纸、材料、方案、计算书、样品、厂家资料的提交与批复记录，集中体现为《提交审批登记台账》（Submittal Register），字段至少包含：编号、名称、提交日期、应批复日期、实际批复日期、批复结果、重提交次数、责任方、对应计划活动 ID。

这条线的杀伤力极大：把台账拉出来一算，业主累计审批超出合同时限多少天，就是一条现成的"业主审批延误"证据。前提是——计划里给了对方时间，台账里记了对方用时。

现场记录线（Site Records）：施工日志、气象记录、人员与机械台账、影像资料、检验与试验记录（ITP 见证记录）、材料进场记录、交接班记录、安全事件记录。

2. 编号贯通，是文控与计划耦合的技术关键

专业的做法是建立统一的编号规则，让三套体系可以互查：

函件编号 ↔ 对应计划活动 ID ↔ 台账条目编号；

提交审批编号 ↔ WBS 编码 ↔ 计划活动 ID；

现场记录日期 ↔ 数据日期区间 ↔ 当期进度测量依据。

做到这一点，当某一天需要证明"A 区域基础之所以晚了 23 天，是因为业主图纸批复晚了 18 天"时，可以在半小时内把函件、批复记录、现场日志、计划对比四条证据同时调出来，指向同一个活动 ID。做不到这一点，则要花几周时间在几十个文件夹里翻找，且很难形成闭环。

3. 几条值得刻在墙上的铁律

任何影响工期或费用的事件，必须在合同规定的时限内形成书面记录。 没有书面记录，等于没有发生。

口头指令必须转书面确认。 现场会上口头同意的事，会后 24 小时内发确认函，注明"如无疑义请书面回复"。对方不回复，也是记录。

会议纪要要明确"决定、责任人、日期"三要素。 没有日期的决定，无法进入计划；没有责任人的决定，无法追责。

业主提供的资料、场地、许可，进场状态要有签收记录。 交地延误、交图延误、许可延误，都是高频索赔事由，也都需要"我何时提出、对方何时给到"的时间戳。

竣工资料与过程资料同等重要。 很多项目在移交时才开始整理资料，此时人员已散、记忆已淡，最后既拿不到竣工证书，也拿不到索赔。

4. 一个清醒的认识

必须强调：做这些不是"好斗"，也不是准备和业主对着干。国际工程的争议解决成本极高（仲裁、专家证人、法律费用动辄数百万美元、耗时数年），真正的目的一直是"不走到那一步"——因为证据完整的一方，往往在谈判桌上就能解决问题；证据缺失的一方，才被迫走进仲裁庭。

文控和计划做好，最大的收益是：你随时能说清事实，因此你随时可以不吵架。 这就是"不为打官司而来，却处处为打官司而准备"的真正含义。

事实上，如果你让业主觉得一旦打官司，你必赢，这个官司就不必打了。

结 语：

六位一体，进度计划是项目的"时间操作系统"

这六重定位不是并列关系，而是层层递进：契约赋予它合法性，界面赋予它责任主体，范围赋予它边界，流程赋予它逻辑，监控赋予它生命力，文控赋予它证据力。

因此，一个真正成熟的国际工程项目，进度计划从来不是计划工程师一个人在电脑前做出来的。它是合同经理、设计经理、采购经理、施工经理、控制经理、文控主管共同会签的产物；它每月更新一次，每次更新都在回答"合同变了吗、界面动了吗、范围改了吗、逻辑还对吗、偏差谁负责、证据留全了吗"。

把进度计划当成一张图，你得到的是一张图。

把进度计划当成项目的时间操作系统，你得到的，是对一个项目真正的掌控。
