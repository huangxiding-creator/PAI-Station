# OBS Route Contract

## Route precedence

1. Name the accepted product and durable state: A1, H1, F1, P1, D1, or R1.
2. Preserve an explicit OBS client or live-output request, but do not open OBS for upstream asset/report work.
3. Check runtime, app, OS, account/platform, protocol, secret, permission, fixture, and recovery gates.
4. Choose the least fragile route that preserves the accepted product.
5. State the route and truth label before mutation.
6. Escalate only for a named retained OBS object, observed route failure, explicit live-client lesson, or consequential output state.

## Truth labels

| State | Completion label | Must not be called |
|---|---|---|
| A1 | Standalone validated media asset | OBS source or scene state |
| H1 | Tested deployed overlay page and URL | Installed OBS Browser Source |
| F1 | File/log analysis, blueprint, inventory, or recovery plan | Applied OBS configuration |
| P1 | Named OBS objects changed by an audited authenticated client and read back | Shipped connector when the runtime is ad hoc or absent |
| D1 | Named OBS Desktop state changed and verified on the current build | Reusable protocol automation |
| R1 | Consequential output state confirmed and independently read back | Safe merely because a request returned success |

## Material questions

- Is the accepted product an asset/page/report, retained OBS configuration, or live output state?
- Which OBS objects must survive: Profile, Scene Collection, scene, source, transform, filter, audio state, capture target, plugin, or output setting?
- Does a compatible authenticated protocol runtime exist now, with a safe secret path?
- Which OS/version/hardware/platform/account constrains the result?
- What disposable fixture and rollback prove the change before production use?

Ask only when the answer changes route, risk, or verification.
